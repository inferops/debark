# Desktop UX visual review

> The capture journals, screenshots and raw logs cited in this document are
> part of the project's internal records and are not published with the
> source. The measurements they back are reproduced here in full.

`hack/ui-review/` serves the actual shell, CSS and screen modules from an
explicit GUI source root. The fixture backend is deterministic, dependency
free, and rejects undeclared/unimplemented calls and invalid response DTOs.
It records binding calls, visible-control journey steps, JavaScript failures, action-area geometry,
focus, horizontal overflow and visible helper-text word counts. It never
returns generic successful results for an absent method.

The original supported Browser skill bootstrap was attempted on this host.
The `mcp__node_repl__js` execution tool failed before executing the bootstrap:
`codex/sandbox-state-meta missing field sandboxPolicy`. GTK/WebKit fixtures
therefore provide fast visual iteration. They are **fixture evidence**, not
real Wails binding, native chooser, close-policy, installation or performance
evidence. Final acceptance separately needs the rebuilt real Wails binary.

The commands below are reproducible procedures, not a claim that each check
has passed. The current inspected evidence and pending checks are recorded in
the outer screenshot index
and implementation record.

## Fixtures and visible journeys

Start the server from the GUI repository:

```powershell
python hack/ui-review/server.py --gui-root . --port 7310
```

Open `http://127.0.0.1:7310/ui-review/index.html?scenario=target&theme=light`.
Use an immutable GUI snapshot for acceptance captures. Do not copy CSS or
screens into the harness directory. Generated
`frontend/wailsjs/go/{models.ts,app/App.d.ts}` define the available methods;
the server fails if parsing misses a declared method or model. Its
`/ui-review/schema.json` includes SHA-256 hashes of both generated source files.

`createFixture` requires this schema. Before cloning a method response, it
recursively checks required fields, field types and unknown fields; it does
not add defaults or strip unexpected fields. Go nil slices/maps may be `null`.
Missing required structs, non-finite numbers, misspelled optional fields and
wrong nested types fail with the method/field path in `fixtureErrors`.
Package rows and selection entries have explicit separate fixture constructors.
Event-only envelopes are not all generated by Wails: directly generated event
payloads and generated nested status/report/summary/error members are checked,
but this is not full generated validation of every event envelope. The
hostile-string harness applies its deliberate text poisoning **after** these
checks. Input arguments are not type-validated here; Go pointer nullability
is not fully represented by the generated TypeScript declarations.

Run the dependency-free checks from the GUI root:

```powershell
# WindowsApps Python aliases cannot always be spawned directly by Node.
$env:PYTHON = python -c 'import sys; print(sys.executable)'
node hack/ui-review/fixtures.test.mjs
node hack/ui-review/job-state.test.mjs
```

On Linux use `PYTHON=python3 node hack/ui-review/fixtures.test.mjs`, followed by
the same job-state command. The fixture suite compares the Python server and
Node schema parsers and exact generated-file hashes, checks 772 responses from
all 52 UI-callable bindings across 31 scenarios, rejects malformed DTOs, accepts nil slices,
and exercises Undo, private URL identity/digests and job transitions. `Bind`
is native startup wiring and deliberately has no pretend-success fixture.
The job-state suite covers separate selection revisions and authoritative,
deduplicated background completion notices.

Pre-W0 baseline bindings do not have the new generation/Undo fields. Current
strict fixtures correctly reject those fields against the old schema. Replay
a baseline with its recorded compatible harness revision and label that
fixture version; do not weaken validation to make old and new surfaces match.
Compare the actual captured default text and controls with this limitation
recorded alongside the before/after images.

Available initial scenarios:

| Family | Scenario identifiers |
|---|---|
| Startup/Target | `startup`, `target`, `target-missing-cli`, `snapshot`, `snapshot-invalid`, `snapshot-cancelled`, `readiness-blocked` |
| Packages | `picker-empty`, `picker-selected`, `selection-many320`, `catalog-loading`, `catalog-missing`, `catalog-failed`, `catalog-cancelled` |
| Bundle | `build`, `build-running`, `build-signed`, `build-unsigned`, `build-incomplete`, `build-failed`, `build-cancelled` |
| Copy | `copy`, `copy-choose`, `copy-choose-cancelled`, `copy-no-space`, `copy-unknown-space`, `copy-incomplete`, `copy-verified`, `copy-skipped`, `copy-mismatch`, `copy-cancelled`, `copy-removed` |

These are seeded states; a screenshot of a seeded result is never called an
end-to-end successful build. Journeys operate visible rendered controls and
record actions/assertions; they fail when a required control is absent,
ambiguous or disabled. Current journey groups are:

| Area | `journey` values |
|---|---|
| Target/menu | `target-continue`, `snapshot`, `main-menu` |
| Preparation | `catalog-retry`, `catalog-cancel` |
| Packages | `search-gimp`, `package-details`, `details-close`, `selection-drawer`, `selection-paging`, `clear-undo` |
| Add | `add-menu`, `add-url`, `url-undo`, `add-files`, `paste-list` |
| Bundle | `build-advanced`, `build-keygen` |
| Copy | `copy-choose-check`, `copy-plan`, `copy-subdir`, `copy-skip`, `copy-cancel`, `copy-another` |

Pair a journey with its appropriate seeded state: `catalog-failed` with
`catalog-retry`, `copy-choose-cancelled` with `copy-choose-check`, or
`picker-selected` with `details-close`. `build-keygen` opens deliberate consent;
it does not prove native key creation. `paste-list` exercises preview, including
unknown/rejected inputs; it does not claim the subsequent Add click. Fixture
keyboard events test handlers and focus state, not trusted native key delivery
or screen-reader speech. Additional journeys must preserve these distinctions.

Pair `selection-many320` with `selection-paging` to check the initial bounded
100-row selection view, Show more to 200, Show all to 320, and removal/Undo of
a middle entry with the original order restored. The journey opens/closes the
named selection drawer when required. Before paging or Undo it waits for
selection reads and focus restoration, scrolls the intended control into the
client viewport, and requires a visible center hit target before clicking.
Failure to settle within the bounded wait remains a failed journey. This is
tray paging evidence, separate from the large catalogue virtualizer benchmark.
Read-only observations are exposed as `window.__UI_REVIEW__`; no shell/store
mutation API is exposed for browser automation.

The package list is small intentional fixture data; it does not measure the
60,000-row performance budget. Use the existing picker-list benchmark with
its stated bridge limitations for that separate measurement. The backend
fixture never acts as an alternate production resolver.

## Immutable capture inputs

Create a new snapshot from the GUI root. `snapshot.ps1` refuses a destination
that already exists, and refuses any destination outside the workspace root it
computes — the directory one level above the GUI root. **The snapshot tree is
capture evidence, not source:** it is never committed and nothing in the build
reads it, so point `-Destination` at a scratch directory kept out of version
control.

```powershell
$captureSnapshot = Join-Path (Resolve-Path ..) 'ux-evidence/snapshots/final-01'
$contentHash = & ./hack/ui-review/snapshot.ps1 -Destination $captureSnapshot
$contentHash
```

`snapshot.ps1` copies `frontend/src`, `frontend/wailsjs`,
`frontend/index.html` and the files in `hack/ui-review`, then writes
`content-manifest.json` with every copied file's SHA-256, including untracked
application and harness modules. Pass the printed manifest hash to
`capture-gtk.py --source-sha256`. Record the corresponding GUI commit and dirty
diff identity separately; a diff hash alone does not identify untracked files.

Run the copied harness from the snapshot. `server.py` serves `/ui-review/*`
from its own directory and application assets from `--gui-root`; launching a
live working-tree runner would mix mutable harness files into a frozen frontend.
Record the harness revision alongside the manifest. Native binaries, external
scratch helpers, container versions and session settings are separate inputs
and still need their own identities. Older snapshots that copied only the
frontend retain that limitation; do not reinterpret their hashes as covering
the harness.

## GTK/WebKit fixture capture

The coordinator owns all containers. Workers provide scripts/commands and
inspect outputs. The established image `debark-a11y:go126` has Ubuntu 24.04,
Python GI, WebKit2 4.1, Xvfb, openbox, xdotool and ImageMagick. Start a session
bus and a sufficiently large virtual desktop before launching windows:

Run the following inside a disposable Linux environment owned by the
coordinator. `/ux/final-01` must contain the immutable snapshot; `/out` is a
deliberate evidence directory. Supply the recorded identity variables rather
than inventing a clean status.

```sh
export GUI_REVISION='<GUI commit for this snapshot>'
export GUI_DIFF_SHA256='clean-or-recorded-patch-sha256'
export GUI_CONTENT_SHA256='<content-manifest.json sha256>'
export ENGINE_REVISION='<recorded engine commit>'
export ENGINE_DIFF_SHA256='<recorded engine patch sha256>'
eval "$(dbus-launch --sh-syntax)"
Xvfb :78 -screen 0 1600x1000x24 -nolisten tcp > /out/xvfb-fixtures.log 2>&1 &
export DISPLAY=:78
export LIBGL_ALWAYS_SOFTWARE=1
export WEBKIT_DISABLE_DMABUF_RENDERER=1
openbox > /out/openbox-fixtures.log 2>&1 &
python3 /ux/final-01/hack/ui-review/capture-gtk.py \
  --gui-root /ux/final-01 --scenario picker-selected --journey details-close \
  --out /out/picker-details-close-light-1040x720.png \
  --revision "$GUI_REVISION" --diff-sha256 "$GUI_DIFF_SHA256" \
  --source-sha256 "$GUI_CONTENT_SHA256" \
  --engine-revision "$ENGINE_REVISION" --engine-diff-sha256 "$ENGINE_DIFF_SHA256"
```

The runner starts its own server, waits for actual modules and fixture calls,
raises/activates the GTK window, captures the client drawable, and writes a
same-name JSON sidecar. It exits nonzero on JS/fixture errors or timeouts.
Use `--width 960 --height 640 --theme dark --zoom 1.25` for the compact,
enlarged-text checkpoint. Record WebKit zoom as such; it is not an OS scale
claim. No screenshot is accepted until a reviewer has inspected it and
replaced `pending-human-inspection` with the outcome. Review blank content,
stale assets, clipping, overflow, focus, readable warnings and anchored actions.

Helper counts derive from visible paragraph/hint nodes in the screen pane,
excluding package rows and monospace content. JSON includes the exact counted
text so a reviewer can exclude user data that happens to use those classes.
They are a density signal, not a substitute for judging comprehension.

The same runner accepts `--demo build` for the actual build module's behavior
checks and `--demo picker-list` for its existing virtualizer benchmark.
These load the standalone module demos with `autorun=1`, not the full shell.
Their reports distinguish behavioral/performance evidence from product-layout
captures. Preserve any benchmark bridge limits and actual sample counts.

## Appearance observations

`appearance.js` exports `observeAppearance(root = document)` for review tools.
After the requested UI/media state has settled, `review.js` attaches its
return value to `observed.appearance`.
The module only reads the current rendered document: it introduces no probe
elements, theme overrides, synthetic focus or preference emulation.

The report records actual media matches, computed token declarations, visible
text colors and composited backgrounds, representative contrast ratios,
currently drawn outlines, and CSS motion durations. Contrast uses computed
element colors because raw tokens can retain unresolved `light-dark()`.
It reports normal-text floor 4.5 and UI-outline floor 3, with separate
inactive-control and unassessed cases. Border ratios are observations; a
decorative separator is not automatically a failed control boundary.

This is evidence for the current visible state only. It does not establish
native-widget contrast, closed details, offscreen content, hover states,
unfocused focus rings, modal backdrops, gradients or opacity groups. Record
actual OS/theme preference changes and their media results; changing an app
theme does not prove increased contrast, and a WebKit engine that reports
`forced-colors: none` has not exercised forced colors. Reduced-motion sampling
does not prove that every possible transition respects that preference.

## Real Wails capture and close/chooser verification

Build frontend assets before compiling the Linux Wails application, using
the repository's documented native tags (`desktop production webkit2_41`)
and the exact recorded engine tree. Record GUI/engine revisions, dirty patch
hashes, binary hashes and build commands separately. Launch under a session
bus with software rendering and a large Xvfb display. A 1600x1000 display lets
both required client sizes fit fully on screen with native decorations.

`native-session.sh` runs the actual rebuilt executable in an isolated desktop.
It requires absolute `UX_APP`, `UX_OUT` and `UX_STATE` paths, uses fresh XDG
cache/config/data directories, adds the executable directory to PATH for the
deliberate test CLI, starts Xvfb/openbox, enables AT-SPI, and records
`session.env`, `app.pid` and logs. Run only inside the coordinator's disposable
Linux environment; never launch these accessibility helpers on the user's
desktop. Choose a fresh state directory and unused display for each session.

```sh
UX_APP=/out/bin/debark-final UX_OUT=/out/native-final UX_STATE=/out/state-final \
  DISPLAY=:79 dbus-run-session -- \
  bash /ux/final-01/hack/ui-review/native-session.sh
```

Keep that session running. In another shell in the same environment, join
its recorded bus/display and inspect or operate showing accessible controls:

```sh
. /out/native-final/session.env
python3 /ux/final-01/hack/ui-review/native-atspi.py tree \
  > /out/native-final/target-accessibility.txt
python3 /ux/final-01/hack/ui-review/native-atspi.py focus Continue --role 'push button'
xdotool key --clearmodifiers Return
```

`native-atspi.py` supports `tree`, `focus` and `activate`, with optional
`--app`, `--role` and `--depth`. It requires exactly one showing named control
for actions and fails on ambiguity. It does not evaluate JavaScript or invoke
Wails bindings. Use its tree output to discover the actual accessible name
and role; send trusted keyboard input with xdotool after focus. AT-SPI tree
inspection alone does not demonstrate Orca speech. Close the app through its
real Quit/window-close flow so the session script can observe process exit and
tear down its own window manager/display.

After launching the actual binary, identify its mapped window, move it on
screen, size the client, and activate it before capture:

```sh
window_id=$(xdotool search --onlyvisible --name '^Debark$' | head -n 1)
test -n "$window_id"
xdotool windowsize "$window_id" 1040 720
xdotool windowmove "$window_id" 20 30
xdotool windowactivate --sync "$window_id"
xdotool getwindowgeometry --shell "$window_id"
xwininfo -id "$window_id"
import -window "$window_id" /out/native-target-1040x720.png
```

Record both actual window and client sizes; window-manager decorations can
add pixels. Native chooser, keyboard focus, close confirmation/default action,
Stop and close cancellation/cleanup, cleanup timeout and active-job revisit
need actual window interaction (AT-SPI/xdotool/manual), not fixture calls.
The fixture `RequestClose` is a minimal bridge model and never evidence that
native confirmations or shutdown cleanup passed.

Keep three evidence levels separate: GTK fixtures prove rendered controls
against deterministic data; native sessions prove real Wails/window/chooser
interaction; `bash hack/demo-gui-e2e.sh` proves binding → CLI → bundle/export
and offline installation with deliberate test keys/paths. A successful binary
build, signed-state label or native chooser does not substitute for the latter
trust/install checks. The updated hostile-string runner separately requires
visible journey/binding coverage, deliberate injection checks and a positive
URL control; a zero-problem result without reached controls is rejected.

Save reviewed images into the UX screenshot evidence tree, one directory per
checkpoint. That tree is kept outside this repository, and existing evidence in
it is left untouched. Link each milestone in its index and record scenario,
revision/diff identity, fixture/live, rendering engine, theme, native/client
dimensions, scaling and inspected outcome. Keep blocked checks explicit.
Prefer coherent committed capture roots. If capturing a dirty tree, hash all
relevant source files, including untracked modules; `git diff` alone omits
new files and cannot establish a complete source identity.

## Recorded final native evidence

`native-perf.py` observes the actual application externally. Its startup mode
launches the supplied test binary in an isolated profile/process group, waits
for native accessible Continue, and cleans up only the group it launched. RSS
mode reads an already idle app's process tree without changing application
state or forcing GC. Run startup after interactive/speech checks so its new
windows do not disturb them. Record the active screen, cache identity, prior
job activity and settling time separately for RSS comparisons.

```sh
. /out/native-final/session.env
python3 /ux/final-01/hack/ui-review/native-perf.py startup \
  --binary /out/bin/debark-final --profile-root /out/perf-state-final \
  --samples 10 --interval 1 --out /out/native-final/startup.json
python3 /ux/final-01/hack/ui-review/native-perf.py rss \
  --pid "$(cat /out/native-final/app.pid)" --samples 10 --interval 2 \
  --out /out/native-final/idle-rss.json
```

The [performance appendix](../performance.md#final-source-native-startup)
records ten accepted-binary launches to a showing, enabled native Continue
button: p50 200.932ms, p95/max 258.566ms. The
source journal
identifies GUI binary SHA-256
`479ff464ac2e9e395a7ad3df4394b4f8acc8ceef468dd956263cae6c0908a41e`.
These are AT-SPI availability upper bounds on a warm OS/profile, display `:90`
at default GDK scale 1, not first-paint or cold-page-cache measurements.
All ten launches reached ready and completed cleanup; preserve the per-launch
logs and any observed retries alongside the aggregate. The earlier scale-2
startup checkpoint remains historical in the performance appendix. Native
memory records also preserve the unresolved 400MB RSS
budget miss and the baseline's excluded desktop-infrastructure rows.

The [accessibility appendix](../accessibility.md#current-native-keyboard-and-speech-evidence)
records actual Stop and close during an 8GiB copy, with process exit and the
incomplete marker retained; it also records close after an unchanged completed
signed build without another confirmation. An X connection closing before
the input driver returns is not a valid elapsed-time result; check the saved
process-exit journal separately. Native HighContrast light/dark captures used
logical 960×640 clients at `GDK_SCALE=2` (1920×1280 captured pixels), with
WebKit zoom 1. They do not establish OS font-only scaling or forced colors.
Later native follow-ups repaired upward list ancestry, Search focus speech and
connectivity, and the retained cursor after Details. Initial list cursor and
selection speech before a Details round trip remains partial; the
[current speech evidence](../accessibility.md#native-list-and-search-follow-up-2041-utc)
records the exact events and the brief first-selected announcement before
cursor correction. Keep these outcomes separate from fixture and backend tests.

### Repeatable external measurements and speech logging

In the dedicated test container, `native-perf.py rss --pid APP_PID --out
/out/session/idle-rss.json --samples 10` reads the app and WebKit descendants
from `/proc`, excluding named Xvfb/openbox/Orca infrastructure. It does not
force GC. `native-perf.py startup --binary /absolute/rebuilt-binary
--profile-root /out/session/perf-profile --out /out/session/startup.json
--samples 10` launches separate owned process groups and records their cleanup.
Join the native session bus/display first. Startup includes AT-SPI polling and
reports accessible Continue availability; it is not a first-paint measurement.

`bash hack/ui-review/native-orca.sh /out/session` configures an isolated
speech-dispatcher dummy output and starts installed Orca with a debug log.
Run this only in the dedicated disposable container: Orca's replacement mode
stops other Orca instances owned by that test user. The accompanying launcher
filters unreapable zombie PIDs from process discovery, because the installed
Orca launcher otherwise waits forever for them in a container without a
reaping init. It does not change speech, events, AT-SPI or application code.
The dummy output records generated speech; it does not prove audible output
or hardware Braille. Retain the complete debug log and a separately timestamped
action journal; debug-file buffering can put speech into a later extracted
action section. Evaluate timestamps, not just adjacent transcript headings.

The export behavior demo is available through `capture-gtk.py --demo export`;
its actual-module assertions cover signature-status recovery and stale reads.
Unknown fixture journey names fail explicitly. A named journey that was never
implemented must not be reported as a passed interaction.
