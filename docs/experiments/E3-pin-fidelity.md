# E3 — Pin fidelity

Script: `hack/experiments/e3-pin-fidelity.sh`. Raw evidence:
`hack/experiments/out/e3/` (regenerated by the script; `summary.txt` is the
curated transcript, `log-*.txt` are the individual raw `apt-get`/`apt-cache`
transcripts this document quotes from).

## Bottom line

**The three defences are sufficient for debark's default
install path (exact `pkg=version`), but not for the `--upgrade` path
(`full-upgrade`), which is also part of the shipped design (step 4).**
Under `--upgrade`, a pin that genuinely changed the online resolution can be
silently reversed on the target with **zero indication anything went wrong**
— `full-upgrade` reports plain success. This is a real gap, found on the
first clean run of the experiment, that none of the three listed defences
catches as written. It does not require per-origin partitioning to become
"needed for v1 GA" wholesale — a narrower fix closes it (see
[What this means for the design](#what-this-means-for-the-design)) — but it
does mean **the open question should not stay parked at "v1.x only if a real
pin case demands it": a real pin case demands a decision now.**

A second, independent finding qualifies the own framing of the problem:
the plain `Pin: origin <name>` preferences keyword — arguably the most common
form third-party-repo pins take in the wild — does not key off the Release
file's `Origin:` field at all. It keys off the archive's **download-site
hostname**. That mechanism is unfixable by any Release-field rewrite,
including per-origin partitioning as currently scoped, because a `file://`
bundle has no hostname to offer. See
[Finding 2](#finding-2-the-bare-pin-origin-keyword-keys-on-hostname-not-on-the-release-origin-field).

## Question

"Pinning versus the flat repository": the target's
`apt_preferences` may pin by origin/label/release; the bundle is one
synthetic flat repo whose `Release` does not carry the original origins, so a
*second* resolution on the target could pick differently. Three defences are
listed: (1) exact-version installs, (2) a closed-world `apt-get -s install
<lock set>` check before export, (3) fixed `Release` fields
(`Origin: debark`, `Suite: bundle`, `Codename: <target>`), with per-origin
partitioning deferred to "v1.x … if a real pin case demands it (experiment
E3)". The design's own experiment table, under "Open questions", frames this as:
*does closed-world `-s install` reproduce the online choice, and is origin
partitioning needed for pinned targets?*

## Method

Real network PPAs would make this experiment non-reproducible (the phasing
state, mirror contents, etc. change over time — this is the exact pitfall E1
hit). Instead this experiment builds two fully controlled, local, flat apt
repositories and never depends on any real third-party archive except as a
one-off confirmatory check in step 7 (against the container's own already-
configured, real, signed `archive.ubuntu.com`, used read-only and never
required for the core result).

1. **Two synthetic origin repos**, each a minimal `equivs`-built placeholder
   `.deb` of the same package name, at different versions, indexed as a flat
   apt repo with `apt-ftparchive … release` (mirrors
   `download-packages.sh` the indexing step):
   - `origin-backports` mimics an Ubuntu `-backports` pocket: `Release`
     `Origin: DebarkE3Backports`, `Suite: noble-backports`. Carries the
     package at **2.0-1** (deliberately the *newer* version).
   - `origin-vendor` mimics a trusted third-party vendor repo: `Release`
     `Origin: DebarkE3Vendor`, `Suite: debark-e3-vendor`. Carries the
     package at **1.0-1** (deliberately the *older* version).

   Newer-but-low / older-but-high is deliberate: it makes "the pin decided
   it" and "the higher version number won" mutually exclusive outcomes, so
   the online resolution result is unambiguous proof pinning worked (not an
   artifact of version-number tie-breaking).

2. **Target private apt root** (idiom: explicit `Dir::*` options,
   `Debug::NoLocking=1`, `APT::Sandbox::User=root`) with a **real** dpkg
   status — the container image's own `/var/lib/dpkg/status` (174 real
   installed-package stanzas), never a hand-written one. (E1's pitfall note
   warns a synthetic single-stanza status makes upgrade-style resolution
   misbehave for unrelated reasons; this experiment sidesteps that
   categorically by never hand-writing a status file at all.) An
   `apt_preferences` file pins:
   ```
   Package: *
   Pin: release a=noble-backports
   Pin-Priority: 100

   Package: *
   Pin: release o=DebarkE3Vendor
   Pin-Priority: 900
   ```
   (Why `release a=`/`release o=` and not the bare `origin`/`release`
   keyword forms — see [Finding 2](#finding-2-the-bare-pin-origin-keyword-keys-on-hostname-not-on-the-release-origin-field);
   this is the form that actually keys off Release metadata, which is what
   the pinning design is about and what defence 3 targets.)

3. **Resolve online**: both origin repos configured as sources, `apt-get -s
   install <bare package name>` (no version) in that root. Record the exact
   selection — this is "the online choice" that would go into the lock. Then
   *really* (non-simulated) install that same package, so a second, equally
   real dpkg status exists with the package already present, for the
   `full-upgrade` test in step 5c. (That real install runs against the
   container's own root, not the newly-constructed private root — see the
   script comment at step 3 for why: a private root built fresh by this
   script has a status file but not dpkg's other admin-directory
   scaffolding, and a real, non-simulated `dpkg` unpack/configure wants that
   scaffolding. The container is disposable — `--rm` — exactly like E1's use
   of the same idiom.)

4. **Two flat bundles**, both laid out
   (`repo/Release`, `repo/Packages`, `repo/pool/<p>/<pkg>/<file>`) and both
   with `Release` written exactly as the design's defence 3 specifies —
   `Origin: debark`, `Label: debark`, `Suite: bundle`,
   `Codename: noble`:
   - **bundle-winner**: only the locked package, `debark-e3-demo_1.0-1_all.deb`
     — what one ordinary debark run produces.
   - **bundle-accumulated**: *both* `1.0-1` and `2.0-1` in the pool. This is
     not a contrived stress case: the design states the **default run is
     additive**, and superseded-version pruning only happens under
     `--update`, where it *still* "never deletes" user-supplied files and
     otherwise prunes by "keep the highest `dpkg --compare-versions`
     version" — a purely numeric rule with no notion of pins (see the caveat
     in [What this means for the design](#what-this-means-for-the-design)).
     A bundle carrying more than one version of a package, including the
     "wrong" (pin-losing) one, is a normal, documented possibility, not an
     edge case invented for this experiment.

5. **Closed-world checks**: fresh private root each time, **same real dpkg
   status**, **the identical `apt_preferences` file carried over
   unmodified** (per defence 3's assumption), sources replaced with *only*
   the flat bundle (`deb [trusted=yes] file://<bundle> ./`). Against each
   bundle: `apt-get -s install pkg=1.0-1` (exact, as debark's real install
   path always does step 4) and `apt-get -s install pkg` (bare
   name). Against bundle-accumulated only, additionally: `apt-get -s
   full-upgrade` with the target's dpkg status now showing `1.0-1` already
   installed (from step 3's real install) — this exercises the design step
   4's `--upgrade` flag, which "runs full-upgrade first".

6. **Isolate the two Release-keyed pin selectors**: two more closed-world
   roots against bundle-accumulated, one with *only* the `release a=`
   stanza, one with *only* the `release o=` stanza, to see whether either
   individually still matches anything once Release no longer carries the
   original Suite/Origin.

7. **Characterise the bare `Pin: origin <name>` keyword** specifically
   (distinct from the `release o=` selector used above), against the real,
   already-configured, signed `archive.ubuntu.com` (chosen because it has a
   real, known `Origin: Ubuntu` Release field *and* a real hostname, so both
   candidate interpretations of "origin" can be tested against a repo where
   we know the truth of both fields, without needing a throwaway HTTP
   server).

Environment for the run quoted below: `ubuntu:24.04` (apt 2.8.3), via
`MSYS_NO_PATHCONV=1 docker run --rm -v /path/to/debark:/src -w /src
ubuntu:24.04 bash hack/experiments/e3-pin-fidelity.sh`, exit code 0.

## Raw evidence

**Online resolution** (`log-02-online-policy.txt`, `log-03-online-install-s.txt`)
— both origin repos visible, pin active:

```
debark-e3-demo:
  Installed: (none)
  Candidate: 1.0-1
  Version table:
     2.0-1 100
        100 file:.../origin-backports ./ Packages
     1.0-1 900
        900 file:.../origin-vendor ./ Packages

Inst debark-e3-demo (1.0-1 DebarkE3Vendor:debark-e3-vendor [all])
```

The pin worked exactly as intended: candidate is `1.0-1` (vendor, priority
900) even though `2.0-1` (backports-like, priority 100) is the numerically
newer version. **Online choice: `debark-e3-demo=1.0-1`, origin
`DebarkE3Vendor`.** This is what would go into the lock.

**Closed-world, bundle-winner** (only `1.0-1` in the bundle) — both exact and
bare-name installs trivially agree with the lock; no divergence is possible
when there is only one candidate:

```
exact-version install debark-e3-demo=1.0-1: OK
bare-name install picks: 1.0-1
```

**Closed-world, bundle-accumulated** (`1.0-1` and `2.0-1` both in the bundle,
**same preferences file, unmodified**) — `log-06b-bundleB-policy.txt`:

```
debark-e3-demo:
  Installed: (none)
  Candidate: 2.0-1
  Version table:
     2.0-1 500
        500 file:.../bundle-accumulated/repo ./ Packages
     1.0-1 500
        500 file:.../bundle-accumulated/repo ./ Packages
```

Both candidates sit at the default priority 500 — neither pin rule matches
anything any more (`Suite: bundle` / `Origin: debark` matches neither
`a=noble-backports` nor `o=DebarkE3Vendor`). Exact-version install still
succeeds (`log-06c-bundleB-exact.txt`, `Inst debark-e3-demo (1.0-1 …)`,
defences 1+2 working as designed). But the bare-name install
(`log-06d-bundleB-barename.txt`):

```
Inst debark-e3-demo (2.0-1 debark:bundle [all])
```

**picks `2.0-1` — the version the online pin explicitly rejected.** Plain
highest-version tie-breaking took over the instant the pin's targets stopped
existing in `Release`.

**`full-upgrade` against bundle-accumulated**, target already has `1.0-1`
installed (`log-07c-bundleB-fullupgrade.txt`) — this is the design step 4's
actual `--upgrade` path, not a hypothetical bare-name misuse:

```
The following packages will be upgraded:
  debark-e3-demo
1 upgraded, 0 newly installed, 0 to remove and 0 not upgraded.
Inst debark-e3-demo [1.0-1] (2.0-1 debark:bundle [all])
```

`full-upgrade` reports this as ordinary, successful, zero-network work — no
warning, no error, no indication the target's own pin (still sitting
unmodified in `preferences.d`) used to forbid exactly this.

**Isolating the two Release-keyed selectors** against bundle-accumulated,
each alone (`log-08b`, `log-09b`) — both individually degrade to priority
500 (inert):

```
-- release a=noble-backports (100) alone --        -- release o=DebarkE3Vendor (900) alone --
     2.0-1 500                                           2.0-1 500
     1.0-1 500                                           1.0-1 500
```

Neither survives independently; it is not that they cancel each other out,
each is individually a no-op once its target Suite/Origin string is gone.

**The bare `origin` keyword vs. `release o=`**, against the real, signed
`archive.ubuntu.com` (`log-10b`, `log-10c`):

```
Pin: origin "Ubuntu"                (real Release Origin: field) -> priority 500 (NOT matched)
Pin: origin "archive.ubuntu.com"    (download-site hostname)     -> priority 900 (matched)
```

## Finding 1: the design's own worry is confirmed, and it lands specifically on `--upgrade`

The exact scenario the design describes — a target pin that changed the
online outcome, then evaluated against a flat repo whose `Release` no longer
carries the pinned-against identity — reproduces cleanly and repeatably.
Whether it matters in practice splits sharply by install path:

| Install path (step 4) | Exact-version? | Result against bundle-accumulated |
|---|---|---|
| `apt-get install pkg=ver` (plain/`--all`/`--status`/`--dry-run`, all read from the lock) | Yes | **Matches the lock every time** — confirmed for both bundles. Defences 1+2 hold. |
| `--upgrade` → `full-upgrade` | **No** | **Diverges**: silently re-selects the pin-losing version, reports plain success. |

Defence 2 as written ("closed-world check… run `apt-get -s install <lock
set>` (and `-s full-upgrade` if applicable); it must succeed with zero
network fetches") technically *is* satisfied by the `full-upgrade` run above
— it succeeds, and it fetches nothing over the network, because the only
configured source is `file://`. **"Succeeds with zero network fetches" and
"produces the plan the lock intends" are different properties, and defence 2
only checks the first one.** That is the precise mechanism by which none of
the three listed defences catches this: #1 doesn't apply (`--upgrade` isn't
an exact-version install), #2's literal check passes anyway, and #3 is the
very thing that made the pin go inert in the first place.

## Finding 2: the bare `Pin: origin <name>` keyword keys on hostname, not on the Release Origin: field

This qualifies how the design frames "pin by origin" in the first place. Two
distinct apt mechanisms both get called "origin pinning" colloquially:

- `Pin: release o=<value>` (part of the `release` selector family, alongside
  `a=`/`n=`/`l=`/`c=`/`v=`) matches the `Origin:` line of the `Release` file.
  **This is what defence 3's Release rewrite (`Origin: debark`) is
  correctly calibrated against**, and Finding 1's divergence is this
  selector losing its match.
- The bare `Pin: origin <name>` keyword — the form shown.5's
  own prose example and probably the more commonly hand-written one for
  pinning a third-party vendor repo — matches the **archive's download-site
  hostname** (`Site()` in apt's own terms), quoted or not. It does **not**
  match the Release `Origin:` field at all: pinning `"Ubuntu"` (the real,
  verified value of `archive.ubuntu.com`'s own `Origin:` field) against that
  same real repository does not raise its priority; pinning the literal
  hostname `"archive.ubuntu.com"` does.

The consequence: for any target `preferences.d` written in this very common
style (`Pin: origin "download.example.com"`), **no Release-field rewrite —
including per-origin partitioning, however it ends up designed — can restore
a match**, because the fundamental issue isn't which strings `Release`
carries, it's that a `file://` bundle has no network hostname at all. A
partitioning design that preserves each original source's `Origin:`/`Suite:`
identity inside the bundle would close Finding 1's gap (the `release o=`/
`release a=` selectors), but this second, probably more common, pin style
would stay broken regardless. This should temper expectations of what
partitioning buys, whenever it is built.

## What this means for the design

**Are the three defences sufficient? No — not as a blanket
statement.** They are sufficient for the plan-from-the-lock, exact-version
install path, confirmed directly. They are **not** sufficient for the
`--upgrade` path, which the design already specifies as running
`full-upgrade` (a free, non-exact-version resolution) against the same flat
bundle. That gap is real, reproduces on the first clean run, and produces no
diagnostic — a target running `debark install --upgrade` against a bundle
that happens to carry more than one version of a package (a normal outcome
of the default additive mode, not a contrived case) can silently end up
on a version its own, still-present pin was written to forbid.

**Should per-origin partitioning move up from "v1.x only if a real pin case
demands it"?** A real pin case demands *a decision*, but not necessarily
*partitioning specifically* — a cheaper fix is available and is more
consistent with defence 1's existing philosophy ("apt is the oracle, but
only ever asked exact questions"):

- **Narrower fix (recommended first)**: make `--upgrade` plan from the lock
  too — resolve the upgrade set online (where pins still have their real
  targets to match against) and install *that* exact plan on the target,
  the same way the plain install path already does, rather than handing
  `full-upgrade` a free hand against the bundle. Equivalently, if a free
  `full-upgrade` against the bundle is kept for convenience, defence 2's
  closed-world check needs to be strengthened from "succeeds, zero network"
  to "succeeds **and its `Inst` lines match the lock's upgrade plan
  exactly", failing the export otherwise. Either change is scoped to the
  install/export code path already being built and does not require
  reshaping the bundle's repository layout.
- **Per-origin partitioning**: would also close Finding 1 (by giving
  `release a=`/`release o=` something real to match inside the bundle
  again), and is the only fix on the table for a scenario the current
  design doesn't cover at all: a `--status`/interactive flow that
  deliberately wants apt's free choice among multiple in-bundle candidates
  to still respect the target's real pin policy. Finding 2 caps its payoff,
  though — it cannot help hostname-keyed `Pin: origin` pins under any
  design, since that mechanism has no Release-field equivalent to restore.

Given the narrower fix fully closes the one concrete gap this experiment
found, **partitioning does not need to become a v1 GA requirement on this
evidence alone** — but the open-questions table's current framing ("v1.x
option only if a real pin case demands it") reads as a *someday* item, and
this experiment is that real pin case arriving on schedule. The `--upgrade`
gap itself (independent of which fix is chosen) should be treated as a
pre-GA fix, not deferred, since it is a silent-failure mode in a shipped
install flag, not a missing nice-to-have.

**One adjacent, not-independently-tested caveat**, surfaced by reading
the design's own pruning rule rather than by running code (there is no Go
pruning implementation yet to test, and this experiment did not write or run
any Go): `--update`'s
prune step is specified as "keep the highest `dpkg --compare-versions`
version" per `(name, arch)`, with no mention of pin priority. Read literally,
that means even the *pruning* step — independent of the `--upgrade`
divergence above — could discard a pin-preferred lower-numbered version from
the bundle entirely in favor of a higher-numbered one the target's pins were
written to reject, before installation is ever considered. This is worth a
deliberate design decision (should prune order respect the target's pins,
where known?), flagged here because it shares Finding 1's root cause
(version-number tie-breaking silently overriding pin intent) but sits in a
different, not-yet-built part of the pipeline this experiment did not touch.

> **Resolved.** This caveat was confirmed against the implementation once it
> existed, and fixed. See [Prune resolution](#prune-resolution) below — the
> failure mode turned out to be a hard build error rather than the silent
> wrong-version ship predicted here.

## Prune resolution

*Appended after the experiment, when the Go pruning implementation this
experiment could not test (`core/bundle/prune.go`) was written.*

The "adjacent, not-independently-tested caveat" closing
[What this means for the design](#what-this-means-for-the-design) — that
`--update`'s prune step, specified as "keep the highest
`dpkg --compare-versions` version" per `(name, arch)`, could discard a
pin-preferred lower version — **is confirmed as a real defect and is now
fixed.** It was reproduced against the implementation, not reasoned about.

**How it actually manifests, which is not what the caveat predicted.** The
caveat anticipated a silent quality degradation: a bundle shipping the
higher version the pins were written to reject. The measured behaviour is
both worse and louder. `assemble` materialises this run's selections into
the pool *before* it prunes (`assemble.go`, `materialiseSelections` then
`pruneExistingPool`), so the plan's own file is on disk and visible to the
pure decision. When an earlier additive run has left a numerically higher
sibling behind, the version-only rule ranks the plan's file below it and
deletes it — after which the repository writer, which indexes exactly that
file, cannot open it:

```
repository: read control data of pool/f/foo/foo_1.0_amd64.deb:
  ... The system cannot find the file specified.
```

So `debark build --update` with pruning **fails outright** whenever the
target's pins select a lower version than a leftover in the pool, rather
than quietly shipping the wrong one. That is a better failure mode than the
one predicted, but it is still a hard break in a shipped flag combination,
and it is triggered by exactly the pin scenario this experiment was written
to investigate.

**The rule adopted.** `PoolEntry` gains a `LockReferenced` flag, set for
every pool file that is one of this run's plan selections — which is
precisely the set the lock will name, since `buildLock` derives
`lock.Packages` from the same `selections` slice. A lock-referenced entry
still *counts* toward what "highest" means, so it can supersede an older
archive sibling, but it is never itself returned for removal. This is the
same exemption `UserSupplied` already had, and the same principle ADR-007
applies one stage later on the install path: **never let a free
re-resolution override what the lock already decided.** Pruning is a free
re-resolution over version numbers; the lock outranks it.

Framing the fix this way, rather than as "prune should respect the target's
pins", is deliberate. Prune does not need to know anything about pins,
priorities, or origins — it only needs to know that the plan already
resolved this question using the target's own apt, which is the oracle
. Teaching the prune step to re-derive pin priority would have been
a second, weaker solver competing with the first.

**Consequence, accepted knowingly.** With the plan's file protected and the
higher leftover still the group's numeric best, neither is removed, so the
leftover survives as dead weight in the pool. It is covered by the manifest
(`manifest.Build` walks the whole bundle dir, so integrity verification is
unaffected) but **not** written into `Packages`, which indexes only this
run's selections. The target's apt therefore cannot see, let alone select,
the version the pins rejected — the property that actually matters here —
at the cost of some bundle size. `TestAssemblePruneKeepsTheVersionTheLockNames`
pins all three facts.

A tighter rule is available and was *not* taken: prune could remove any
leftover that is neither lock-referenced nor user-supplied regardless of
version rank, since nothing in the bundle references it. That would reclaim
the wasted bytes, but it changes `--update` from "additive with supersession"
to "additive with garbage collection", which is a design decision rather
than a bug fix, and it would silently discard files an operator may be
relying on across runs. Left as an open question rather than folded into
this fix.

**Verification.** Reverting the one-line exemption in `pruneDecide` makes
both `TestPruneNeverReturnsLockReferenced` and the product-level
`TestAssemblePruneKeepsTheVersionTheLockNames` fail, the latter with the
`repository: read control data` error quoted above; restoring it makes them
pass, with `go build ./... && go test ./...` clean. The product-level test
asserts against the `lock.json` that `Assemble` actually wrote rather than a
hardcoded path, so it cannot pass vacuously if the plan or pool layout
changes.

## What could not be completed

Everything in the [Method](#method) section above ran successfully in a
single clean session (`hack/experiments/out/e3/summary.txt`, exit code 0,
regenerable by re-running the script). Two intentional scope limits, not
incomplete work:

- The "real `noble-backports` pocket" alternative mentioned as optional in
  the experiment brief was not used — the fully synthetic, two-controlled-
  repo design was chosen instead (see [Method](#method) step 1) for
  determinism and because it makes the version-vs-pin distinction provable
  by construction rather than by whatever happens to be in `-backports` on
  the day the script runs.
- Finding 2's hostname-keyed mechanism was confirmed against the real
  `archive.ubuntu.com` rather than by standing up a throwaway HTTP server
  for the synthetic vendor repo, since the mechanism being tested (apt's
  `Site()`/download-host comparison) is generic to any HTTP(S) source and
  does not depend on which one is used; a `file://` source cannot host this
  comparison at all (no hostname), which is itself part of the finding.

## Addendum, 2026-09-05: the kept leftover is now reported

*Appended after the fact, like [Prune resolution](#prune-resolution) above.
Nothing before this heading has been edited — this records one later change
that lands on the open question that section left standing.*

"Consequence, accepted knowingly" was accepted without any reporting. The
surviving leftover was in the pool, in the manifest and inside the
operator's signature, and in neither `last-run-added.txt` nor
`last-run-removed.txt`, because the run had neither added nor removed it.
Nothing an operator or auditor reads said it was there.

`core/bundle/unreferenced.go` closes that reporting gap and only that gap.
After prune, every file in `repo/pool` that this run's `repo/Packages` does
not index is written to `last-run-unreferenced.txt` — repo-relative and
sorted like its two siblings, and written before `manifest.Build` so the
report is itself covered by the manifest and the signature. The same set is
raised as a `pool.unreferenced` warning in `lock.json`, which carries it
into the `build` output, `README.txt`'s Warnings section and `debark
inspect`; `evidence.json`'s `bundle.assembled` event carries the count. The
warning names the file and, where the same package *is* indexed at another
version, both versions. Nothing about what prune removes changed: the
`LockReferenced` rule above stands unaltered, and the scan runs on every
build, not only pruning ones.

That last detail matters for reading this section correctly. The pin case
analysed above is not the common way a leftover appears. The same shape
arises with no pin at all: a package an earlier request named and a later
one does not is superseded by nothing, so it survives whatever the prune
flag says. The report is written unconditionally because that case is the
one most operators will actually meet.

This does not answer the open question above, but it does inform it. The
tighter rule was left open partly because "the wasted bytes" was an
abstraction with no reader; an operator can now see exactly which files, and
how many, in the same lock they already read. That is real input to whether
`--update` should ever gain garbage collection — and to the objection that
weighed against it, that such a rule "would silently discard files an
operator may be relying on across runs", which is now a checkable claim
rather than a hypothetical.
