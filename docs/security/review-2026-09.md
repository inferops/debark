## 1. Executive summary

An operator or auditor can read this section alone.

Nine findings were rated Critical or High. **Both Critical findings are
fixed** — one committed, one landed in the working tree during the review —
and both were confirmed by execution rather than argued from reading:

- A captured `apt.conf.d` fragment could execute arbitrary commands on the
  builder. A snapshot is untrusted input by construction, and the filter that
  sanitised it was a deny-list naming only two families. Everything else was
  carried into the private apt root verbatim, including the keys apt does not
  read but **executes** through `/bin/sh`. Confirmed in a container against
  apt 2.6.1: the hook ran as root and `apt-get update` still exited 0, so
  nothing downstream saw anything wrong. This is arbitrary code execution as
  the build user on the one host in the pipeline holding a signing key. Fixed
  in commit `98b9127`; being replaced by an allow-list now.
- A poisoned object in the content store reached a signed bundle with no
  content check anywhere on the path. The manifest then hashed the attacker's
  bytes, so the bundle verified clean on the target. Fixed.

Of the seven High findings, four are fixed and three remain open, all three in
`core/sign` and all three now being fixed:

- **A signature made by a revoked key verifies as valid.** Revocation is the
  only remedy available after a release key is compromised, so a signer that
  silently accepts a revoked key is worse than no gpg support at all. Open,
  fix in progress.
- **`gpg` verification cannot be pointed at a keyring.** The field exists but
  no flag or config key reaches it, so every gpg check runs against whatever
  is already imported in the verifying machine's default keyring, with
  `--trust-model always`. `core/verify` prints remediation advice naming a
  flag that does not do what the advice says. Open, fix in progress.
- **An honest gpg round trip fails** for any key with a separate signing
  subkey — with the loudest tamper verdict the product has. Open, fix in
  progress.

Determinism — a stated non-negotiable — was violated in four ways. Three are
fixed. One remains: no signed bundle is ever byte-identical, because the
signature block's `created_at` reads the wall clock and ignores
`SOURCE_DATE_EPOCH`.

**What was verified sound matters as much as what was not.** The zero-telemetry
claim holds and is now proven rather than asserted: `go list -deps
./core/install` returns 129 packages with **zero** `net/*` among them, so
target-side code physically cannot open a socket. Verify-before-apt holds on
every install path, confirmed by execution against a full tamper matrix — every
case exited 4 and none reached apt or dpkg. apt remains the oracle: there is no
hand-rolled dependency solver anywhere. The full list is §8.

Two documentation gaps were found and both closed during the review:
`docs/security-model.md` described the pre-fix verify, and
`docs/threat-model.md`'s attack table had no row for link substitution.

## 2. `core/apt`

### 2.1 — A captured `apt.conf` fragment executes commands on the builder

**Severity:** Critical.
**Confirmed by execution** (container, apt 2.6.1).
**Status: FIXED, committed `98b9127`. Being replaced by an allow-list now —
see "Final resolution" below.**

**Where:** `core/apt/aptconf.go`, `filterAptConf` and `dropConfReason`.

Before the fix, `filterAptConf` was a deny-list of exactly two families:
anything under `Dir::*`, and `Acquire::*::Proxy`. Everything else in a
captured fragment was preserved and re-serialised into the private apt root.

**What an attacker does.** The chain is short and lies entirely inside the
product's normal input path. A snapshot is untrusted by construction — a file
produced on another machine and carried across the gap on removable media. Its
`apt.conf.d` fragments are copied into the private root, and
`writeAptConfigLoader` points `APT_CONFIG` at that directory *precisely so apt
really reads it* (the mechanism experiment E4 established as the only one that
works). Every resolve then runs `apt-get update` against it. A fragment
declaring `APT::Update::Pre-Invoke` — which apt runs through `/bin/sh` in
`RunScripts()` — is arbitrary code execution as the build user, on the one host
in the pipeline that holds a signing key, at the moment of every build.

Measured with a fragment of exactly the shape the filter preserved:

```text
apt-get update rc=0
HOOK EXECUTED -> uid=0(root) gid=0(root) groups=0(root)
```

The hook runs as root and `apt-get update` still exits 0, so nothing
downstream observes anything wrong. The security model budgets for a malicious
source, and even for a key that makes one look authenticated; it does not
budget for code execution on the builder.

Notably the filter *already* dropped `Dir::Bin::gpgv`, so the obvious "swap the
verifier binary" attack had been anticipated. The hook keys simply were not on
the list — which is how deny-lists fail.

**Interim fix (committed, verified against the code).** The deny-list was
widened to drop: the `Pre-Invoke`/`Post-Invoke` families,
`Post-Invoke-Success`, `Post-Invoke-Stats`, `Pre-Install-Pkgs`,
`Proxy-Auto-Detect`/`ProxyAutoDetect` (`hookKeys`); the whole `DPkg::Tools::*`
subtree; `Acquire::gpgv::Options`, which passes arbitrary argv to the signature
verifier; and the keys that switch apt's own signature and freshness checking
off — `AllowUnauthenticated`, `AllowInsecureRepositories`,
`AllowDowngradeToInsecureRepositories`, `AllowWeakRepositories`,
`Check-Valid-Until`, `Check-Date`, `Verify-Peer`, `Verify-Host`
(`verificationKeys`). A target may legitimately run with the last group set,
but honouring them here would disable apt-secure on the *builder*, which is
where packages are actually fetched over the network; resolution fidelity is
not worth the builder's trust anchor.

The hook and verification keys are matched on the **final path segment**, so a
scoped re-entry such as `Binary::apt-get::DPkg::Pre-Invoke` is caught by the
same rule rather than needing its own. Withholding goes through the existing
`DroppedConfEntry` machinery, so it is recorded in the lock rather than silent.
The fidelity half is pinned by its own test: `Install-Recommends`,
`Install-Suggests`, `Solver`, `Default-Release`, `Languages` and
`Architectures` must still survive, or the bundle stops matching the target.

**Final resolution (fix in progress, not yet landed).** The durable fix is to
turn `filterAptConf` into an **allow-list**: permit only the keys that affect
apt's *resolution*, drop and record everything else through the same
`DroppedConfEntry` path. This is a design decision, not a security patch,
because it trades against faithfully reproducing the target's apt behaviour —
which is why it was made deliberately rather than folded into `98b9127`.

The decision includes one point worth recording explicitly, because it is the
kind of thing a later reader will be tempted to undo: **there is deliberately
no escape-hatch flag.** An `--apt-conf-passthrough` option was considered and
rejected. Such a flag would be reached for to silence the dropped-key warning,
and setting it hands the vulnerability straight back — the operator most likely
to set it is the one who least understands what it re-enables. The remedy for a
genuine fidelity loss is to add that specific key to the allow-list: a small,
reviewable, auditable change with a named beneficiary, rather than a blanket
opt-out.

*Verified against the code:* `hookKeys` and `verificationKeys` are present and
populated as described; `dropConfReason` applies the `Dir` rule, the proxy
rule, both final-segment loops, the `DPkg::Tools` subtree rule and the
`Acquire::gpgv::Options` rule. `aptconf_test.go` carries both halves —
the drop tests and the fidelity tests. The allow-list had **not** landed as of
the closing timestamp; `filterAptConf` is still the widened deny-list.

### 2.2 — `--approved-keys` was enforced against the snapshot's own claims

**Severity:** High.
**Confirmed by execution** (two bypasses).
**Status: FIXED in the working tree** (`core/snapshot/keyringverify.go`, new
file).

`docs/threat-model.md` §3.2 names `--approved-keys` as *the* control against a
snapshot carrying both a malicious source and the key that authenticates it.
It was enforced against `Snapshot.KeyringFingerprints` — a field written by the
target, which is the untrusted side of the gap — and never against the key
material the snapshot actually carried. Two tamperings were free, and both were
confirmed: swap a keyring file's bytes while leaving the recorded fingerprints
naming the genuine archive key; or record a fingerprint for a keyring the
snapshot does not carry at all. Both produce a document that verifies against
itself, because nothing re-derived anything.

**Fixed by** `verifyKeyringFingerprints`, called from `doOpen` after
`verifyExtractedFiles`. It re-derives every fingerprint from the extracted
bytes and refuses a document that disagrees **in either direction** — a claimed
fingerprint the bytes do not contain, and a key the bytes *do* contain that the
document failed to record. The second direction is the one that is easy to
forget: it is how a keyring smuggles in an extra key no audit of the document
would ever show. A keyring whose bytes are not a parseable OpenPGP keyring is
not itself a refusal (capture tolerates one, and an honest snapshot can carry
one) but contributes zero fingerprints, so nothing can ever be approved on its
account. Fail-closed, deliberately.

`checkApprovedKeys` (`core/apt/root.go`) is unchanged in shape and still
correct: a source file passes only when every path-form `Signed-By` resolved to
an approved fingerprint, and a file with no path-form `Signed-By` at all fails
closed.

### 2.3 — Attacker-influenced strings become apt options (no `--` terminator)

**Severity:** Medium. **Reasoning only** — not exercised.
**Status: OPEN.**

**Where:** `core/apt/local.go`, `simulateInstall` and `fetchAndBuildSelections`
(`apt-get -s install <names>`, `install --print-uris -y <pinned>`,
`--download-only -y install <pinned>`); the same shape at
`core/install/runner.go` (`-s install <names>` and `install <names>`).

No call site emits a `--` terminator before the package names, and nothing in
`core/apt` validates a name against Debian's package-name grammar before it
becomes argv. A name beginning with `-` is read by apt as an option rather than
as a package. `core/repository` has `ValidPackageName` and uses it — this path
does not call it.

Reachability is the reason this is Medium and not High: the names come from the
operator's own request and from external `.deb` control fields, and the
`core/install` side reads them from a lock that verification has already
proven. It is cheap to close — an explicit `--`, plus the grammar check
`core/repository` already implements — and should be closed the next time these
call sites are touched.

### 2.4 — `VerifiedAPTSigned` on a source where nothing was verified

**Severity:** Medium.
**Status: PARTIALLY FIXED. A residual remains — reasoning only.**

`fetchAndBuildSelections` stamps every selection `lock.VerifiedAPTSigned`,
which is right for the overwhelming common case (a file apt fetched from an
archive whose `InRelease` it verified) and wrong for anything resolved through
a `deb [trusted=yes] file://… ./` source, where `trusted=yes` means *nothing
was verified*. Recording `apt-signed` anyway claims, in the one record an
auditor reads for provenance, a check that never ran.

**Fixed for debark's own external staging repo:** `Resolve` now re-stamps
every `ReasonExternal` selection `lock.VerifiedURLUnverified`, matching the
choice `core/fetch`'s `FromLocalFile` already made for its own local-file
inputs, so the two paths never disagree about the provenance of what is, from
an auditor's chair, the same kind of input.

**Residual:** a source captured from the *target* that carries `[trusted=yes]`
in its own `sources.list` is still stamped `VerifiedAPTSigned`. I found no
check that inspects a captured source's options for `trusted=yes` and
downgrades accordingly. I did not construct a snapshot to exercise this, so it
is reasoning-only.

### 2.5 — A GPG error apt tolerated reaches no durable record

**Severity:** Medium. **Reasoning only.**
**Status: PARTIALLY ADDRESSED; residual OPEN.**

`ParseUpdate` records `GPGErrors` on every run and renders them through
`UpdateResult.Error()`. `Failed` is driven by apt's own exit code plus a
top-level `E:` line, deliberately and now documented as such: apt retries a
failed per-item acquire internally, and a retry that eventually succeeds is not
a failure. That reasoning is sound and is the right default — apt is the
oracle.

The residual is what happens when apt exits 0 *despite* a GPG error. `Resolve`
consumes only `upd.Failed`, and the evidence event carries a count and a
boolean. So the parsed `GPGErrors` are dropped: they reach neither `lock.json`
warnings nor evidence detail, and an operator reviewing the build has no record
that a signature check on a source went wrong but was tolerated. The fix is
small — fold non-empty `GPGErrors` into `warnings` regardless of `Failed`.

### 2.6 — `ParseSimulate` no longer drops lines, but nothing acts on that yet

**Severity:** Medium.
**Status: HALF-LANDED — parser fixed, caller missing. OPEN.**

`ParseSimulate` used to silently discard any `Inst`/`Conf` line its regexp
could not read, and still report success. A dropped action never enters the
version set, is never fetched, and its absence is later reported to the
operator as the reassuring "already satisfied" case — so a build succeeds with
a package missing from the closure.

The parser half is fixed: `SimulateResult.UnparsedActions` now collects every
line that announced itself as an action (`instConfPrefixRE`) but that
`instConfRE` could not read.

**But it has no consumer.** `UnparsedActions`' own doc comment instructs
callers to "treat a non-empty `UnparsedActions` as a hard stop (see
`simulateParseError` in `local.go`)" — and `simulateParseError` **does not
exist**: a tree-wide grep for that identifier returns nothing, and the only
references to `UnparsedActions` anywhere are its declaration and the line that
appends to it. Until a caller reads it, the field records the defect without
preventing it. Most likely this is mid-flight elsewhere; recorded so
it is not mistaken for finished.

### 2.7 — Multi-keyring `signed-by=` silently de-pinned

**Severity:** Medium. **Status: FIXED in the working tree.**

A deb822 `Signed-By` is a *list* — several keyrings separated by a comma or
whitespace — and `signed-by=/a.gpg,/b.gpg` appears on entirely ordinary
targets, so nothing attacker-controlled was needed to reach this. Reading the
whole value as a single path made every multi-keyring pin fail to resolve and
so be stripped, quietly widening that repository from "verifiable by its own
two keys" to "verifiable by anything in the private root's combined
`trusted.gpg.d`".

Fixed by `splitSignedByValue` and `rewriteSignedByList` (`core/apt/sources.go`),
which rewrite each entry independently. The `private-root.signed-by-stripped`
warning now fires only when **not one** entry survived — the only case where
the source genuinely stops being pinned to its own keys.

## 3. `core/store` and `core/bundle`

### 3.1 — A poisoned store object reached a signed bundle unchecked

**Severity:** Critical. **Status: FIXED in the working tree.**

**Where:** `core/store/fsstore.go` and `core/bundle/assemble.go`
(`ensureInStore`, `materialiseSelections`).

The store is a content-addressed tree of **ordinary files**. Anything able to
write one file into it could park its own bytes behind a digest apt had
vouched for, and nothing on the path from there to the signed bundle ever
opened the object to check:

- `ensureInStore` early-returned on `Has(digest)` without opening the object.
- `PutFile` returned success on `Has(digest)` without checking the held
  object — and, when the caller passed `moveOK`, **deleted the genuine
  download** as a redundant duplicate of the planted one.
- `Materialise` hardlinked without hashing.

The manifest is then built from the pool, so it hashes the attacker's bytes and
the bundle verifies clean on the target. Everything downstream — the `Packages`
index, the manifest, the operator's signature — agrees with itself about the
wrong content. Hardlinking compounded it: writing into an old bundle's pool
file rewrites the store object in place, and a bundle directory is far more
exposed than a store.

**Fixed, in layers**, which is the right shape for a property this central:

- `Store.Open` returns a `verifyingReader` that hashes on the way out and
  refuses a clean EOF unless the bytes match the address.
- `PutFile`'s dedup shortcut (`putByDedup`) re-reads the held object and checks
  it before agreeing to skip the copy; a mismatch falls through to ingest for
  real, which repairs the object.
- `PutFile`'s move fast path (`putByMove`) renames the source into a private
  staging name *before* hashing it, so nothing can swap its content between the
  hash and the publish.
- `Materialise` re-hashes what actually landed at `dest` — unconditionally, a
  full extra read per object — and removes the file on mismatch. Checking
  `dest` rather than the source also covers the copy fallback and the
  hardlink-rewritten-in-place case.
- `ensureInStore` re-ingests a staged copy rather than trusting `Has`, and
  reads an object back in full (`verifyStoreObject`) when there is no staged
  copy behind it.
- `materialiseSelections` then checks the pool file independently of whichever
  `Store` implementation placed it — because `Assemble` takes the *interface*,
  and a security property may not depend on which implementation was passed in.

That last point is the one worth generalising: two of these six checks are
redundant on the current implementation and are there anyway, because the
interface boundary is exactly where "the implementation does it" stops being
true.

### 3.2 — `fsStore` accepted any string as a digest

**Severity:** High. **Status: FIXED in the working tree.**

`Path`, `Has`, `Open` and `Materialise` took the caller's "digest" and appended
it to the store root, so `../../etc/shadow` named a real file that `Has`
confirmed, `Open` read and `Materialise` copied into the bundle the operator
then signed — an arbitrary-read and exfiltration primitive reachable from
anything that could influence a digest string. `digest.Valid()` existed in the
tree and was never called.

Fixed by `address()`, which lowercases and runs `digest.Valid`, and is now the
first thing every entry point does. `Path` returns `""` for a non-address, so a
malformed digest cannot resolve to a path at all; `Has` reports absent; `Open`
and `Materialise` return a `Usage` error naming the offending value.

### 3.3 — Import bounds were per-entry only

**Severity:** High. **Confirmed by execution.**
**Status: FIXED in the working tree.**

`core/bundle/tar.go`'s `importTar` bounded a single entry at 8 GiB and bounded
nothing else — not how many entries an archive may contain, nor how many
decompressed bytes it may produce in total. Neither follows from the per-entry
limit: an attacker who cannot exceed 8 GiB in one entry simply writes more
entries, which is exactly what makes an expansion bomb cheap. Measured: a 68 KB
archive expanded to 2 GiB in 2.9s; a 552 KB archive created 200,000 files. (The
in-code comment records a second pair from the same family: 232 KB → 2 GiB in
1.8s, and 137 KB → 50,000 files in 13s.) Both returned nil.

The reachability is what makes this High rather than Low: `debark inspect`
and `debark doctor` on freshly arrived media run `importTar` **before**
`verify.Verify` has looked at anything. This is the first code to touch the
medium.

Fixed with `maxImportEntries` (50,000) and `maxImportTotalSize` (64 GiB),
both derived from real corpus measurements rather than picked round —
~28× the file count and ~50× the byte count of the largest measured `.deb`
corpus in the repo. Also added: entry-name length bounds
(`maxImportEntryNameLen` 1024, `maxImportNameComponentLen` 255), so an absurd
name is refused as hostile input rather than surfacing as an operating-system
"name too long" that `importTar` would classify as `Environment` — blaming the
operator's machine for a string the attacker chose; and `collisionKey`, which
refuses two entries that resolve to one file under Windows' case-folding and
trailing-dot-stripping rules, on every platform rather than only where it
happens.

### 3.4 — `embedBinary` joined an unvalidated architecture

**Severity:** High. **Confirmed by execution.**
**Status: FIXED in the working tree.**

`Target.Arch` reaches `embedBinary` from the snapshot or from `--arch`
(`Options.ArchOverride`, not validated upstream) and became part of a file
name with no containment check. `Target.Arch = "../../../../PWNED-ARCH"` wrote
a 0755 executable four directories above the bundle root — confirmed.

Fixed with `plausibleArch` plus an `isInside(destDir, dest)` check: a validated
arch should already be containment-safe, so the second check confirms it rather
than assuming it. This is the same layered shape as the `PoolPath` fix the
first review's F1 produced, and deliberately so.

## 4. `core/sign`

All three findings in this section are **open**, all three are being fixed now,
and the decision behind that is worth recording. The alternative on the table
was to narrow the promise — document gpg support as best-effort — or drop it.
That was rejected: **a signer that silently accepts a revoked key is worse than
no gpg support at all**, because revocation is the only remedy available after
a release key leaks. Shipping a check that returns "valid" for a key its owner
has publicly repudiated does not merely fail to help; it actively tells the
operator the thing they most need to disbelieve. If the product offers gpg, it
has to honour gpg's own verdicts.

### 4.1 — A signature made by a REVOKED key verifies as valid

**Severity:** High. **Reasoning only** — I did not run gpg against a revoked
key; the finding rests on reading `parseVerifyStatus` against GnuPG's
documented status-line contract.
**Status: OPEN, fix in progress.**

**Where:** `core/sign/gpg.go`, `parseVerifyStatus` and `gpgVerifier.verify`.

`parseVerifyStatus` scans `gpg --status-fd 1 --verify` output for exactly two
lines, `VALIDSIG` and `BADSIG`. GnuPG emits `VALIDSIG` for a cryptographically
good signature *including* one made by a key that is revoked or expired,
alongside a separate `REVKEYSIG` / `EXPKEYSIG` / `EXPSIG` line carrying that
verdict. Those lines are never read. `ERRSIG` is not read either.

Independently, gpg's own exit status is discarded: `runGPG`'s error is captured
into `runErr` and used only to decorate a message on the failure branch, so
even where gpg exits non-zero the outcome is decided solely by whether a
`VALIDSIG` line appeared.

**The fix in progress** is to honour `REVKEYSIG`, `EXPKEYSIG`, `EXPSIG` and
`ERRSIG`, and to require gpg exit 0.

### 4.2 — `gpg` verification cannot be pointed at a keyring

**Severity:** High. **Confirmed by code inspection and a tree-wide search.**
**Status: OPEN, fix in progress.**

`sign.KeySource.GPGKeyring` is the field that produces
`--no-default-keyring --keyring <path>`. It is **unreachable**: a tree-wide
grep finds it set only inside `core/sign` and `core/verify` tests. No CLI flag
and no config key writes it. `internal/cli/cmd_verify.go` and `cmd_install.go`
both define a `--keyring` flag, and both map it to `KeySource.Dirs` — the
directory of ed25519 public key files — not to `GPGKeyring`. `internal/cli/config`
offers `verify_keys` and `verify_keyring_dirs`, which land in the same two
fields.

So every gpg verification the product performs runs against the ambient default
keyring of whatever machine ran `verify` or `install`, with `--trust-model
always`. The trust set is whatever happens to be imported there for reasons
unrelated to debark.

This is a genuine regression against the first review's intent. F4 recorded the
empty-`GPGKeyring` fallback as documented gpg behaviour and recommended that
`verify` say so in its report. That warning was implemented — and it now reads:

> a gpg signature verified against this machine's default GPG keyring (no
> `--keyring` was given); … pass `--keyring` pointing at a keyring containing
> only the expected release key(s) to narrow it

An operator who follows that advice exactly sets `Dirs`, leaves `GPGKeyring`
empty, does not narrow the gpg trust set at all, and **does not even silence
the warning** — the condition is `opts.Keys.GPGKeyring == ""`, which is still
true. Remediation advice that names a flag which does not do what the advice
says is worse than no advice: it converts a caveat the operator would have
escalated into one they believe they have handled.

**The fix in progress** is a real `--gpg-keyring` flag reaching
`KeySource.GPGKeyring`, and correspondingly honest warning text.

### 4.3 — Primary key fingerprint recorded, signing subkey fingerprint compared

**Severity:** High. **Reasoning only** — established by reading both sides
against GnuPG's `VALIDSIG` field layout; not reproduced with a real subkeyed
key.
**Status: OPEN, fix in progress.**

`gpgSecretKeyFingerprint` records the **primary** key's fingerprint:
`parseColonFingerprint` explicitly tracks `sec`/`pub` versus `ssb`/`sub` and
returns only the `fpr` following a primary record. That value becomes
`Signature.KeyID`.

On the verifying side, `gpgVerifier.verify` compares `sig.KeyID` against field 1
of `VALIDSIG`, which is the fingerprint of the key that **made** the signature —
the signing subkey, when one exists. (The primary key's fingerprint is the
*last* field of `VALIDSIG`, and is not read.)

So for any key with a separate signing subkey — the ordinary, recommended
layout for a release key — an entirely honest sign/verify round trip produces:

```text
sign: gpg signature claims key <primary> but gpg validated it against <subkey>
```

which `core/verify` classifies as `dferr.Verification`, i.e.
`ProblemSignatureInvalid`: *"a signature from a trusted key does not verify
against this manifest"* — the loudest tamper verdict the product has, raised
against a bundle nobody touched. This is a false-positive failure of the exact
alarm the whole product exists to raise, which erodes the alarm's credibility
in the one direction that matters.

**Why the existing test did not catch it:** `core/sign`'s round-trip test
generates a key with no subkey, so the primary fingerprint and the signing
fingerprint are the same string and the comparison passes for the wrong reason.
See §6.2.

### 4.4 — Two unbounded hangs and an orphaned child in the plugin signer

**Severity:** High. **Confirmed by code inspection.** **Status: OPEN.**

**Where:** `core/sign/plugin.go`.

- `newPluginSigner` starts the plugin with `exec.Command(path)`, not
  `exec.CommandContext`. Cancelling the caller's context does not kill the
  child, so an orphaned plugin process outlives the host command.
- The handshake read is a bare `reader.ReadString('\n')` with no context
  involvement. A plugin that starts and says nothing hangs the build
  indefinitely — before any of `call`'s timeout machinery is reachable.
- Inside `call`, `callCtx` (with `defaultPluginTimeout` when the caller's
  context has no deadline) is established, and then `p.stdin.Write(line)`
  runs **before** the `select` that watches it. A plugin that never drains its
  stdin blocks that write forever with the timeout already constructed and not
  yet being waited on.

The third is the subtle one: the timeout looks present at a glance because it
is created two lines above the blocking call it does not cover.

### 4.5 — The signature block's own metadata is not covered by the signature

**Severity:** Medium. **Confirmed by code inspection.** **Status: OPEN.**

What is signed is `SigningInput(purpose, canon)` — the domain-separation string,
a NUL, and the canonical **manifest** bytes. The fields of the
`manifest.Signature` block itself are not in that payload.

`SignerKind` and `Algorithm` are indirectly constrained, because
`compositeVerifier.Verify` routes on them and a wrong route fails. But that
constraint is weaker than it looks: a block labelled `SignerKind:
"plugin:acme-hsm"` with `Algorithm: ed25519` routes to the ed25519 path,
verifies against a trusted ed25519 key, and is then **displayed** as having
come from an HSM plugin. `CreatedAt` and `Comment` are unconstrained outright.

So the provenance an operator reads off a verified bundle — who signed it, when,
and the operator's own note about which key — is forgeable by anyone who can
rewrite the `.sig` file, on a bundle that still verifies. The signature proves
the manifest; it does not prove the story told about the signature.

### 4.6 — A plugin's returned signature is validated only as non-empty base64

**Severity:** Medium. **Confirmed by code inspection.** **Status: OPEN.**

`pluginSigner.Sign` checks that `sr.Signature` is non-empty and decodes as
standard base64, then writes it into the manifest signature block along with
whatever `sr.KeyID`, `sr.Algorithm` and `sr.SignerKind` the plugin returned.
Nothing verifies that the returned bytes are a signature over the payload that
was sent, by the key the plugin claims. A plugin that is merely buggy — signing
a stale payload, or returning a well-formed signature from the wrong key —
produces a bundle that fails verification later, on the target, past the air
gap, where the failure is indistinguishable from tampering.

The check is cheap for the ed25519 case (the public key is available through
`key_info`) and is the standard defence for any delegated-signing interface:
verify your own signature before shipping it.

## 5. Determinism

Determinism is a stated non-negotiable (build the same request twice,
get byte-identical bundles). Four confirmed violations. **Three are
fixed; one is open.**

### 5.1 — The random temp work root reached `ClosedWorld.CommandDigest`

**Status: FIXED in the working tree.**

`CommandDigest` is `canonical.Digest` over the apt argv, and that argv carries
18 `-o Dir::*=<path>` options all derived from a subdirectory of the engine's
`mkdirTemp("", "debark-build-*")` work root. `OutputDigest` is the SHA-256 of
apt's own captured output, and `apt-get update` echoes the `file:` URI naming
the finished bundle's `repo/` directory. Both are `lock.ClosedWorld` fields, so
both reach `lock.json` → `LockDigest` → `manifest.BundleID` → `README.txt`.
Measured: `0e8ebdf6…` vs `1c5b713a…` for two work roots; `985157f8…` vs
`606cccff…` for two output directories — both runs otherwise identical, both
"Result: ok". The check is **on by default**, so this was the ordinary path.

Fixed by `closedWorldMasks` and `maskHostPaths`, applied in exactly one place
(`closedWorldResult`) so a future return path cannot forget it. The masking
replaces only the varying prefix, never the whole entry, so the `Dir::*` keys
and apt's sentence structure survive and an auditor can still see which paths
apt was pointed at.

This was the same defect, on the same kind of value, that
`sanitizeAPTOptionsForLock` already fixed for `Resolver.APTOptions` — that
function was simply never applied on this path. Recorded because it is the
second occurrence, and the third is now guarded against (below).

### 5.2 — `Stats.DownloadedBytes` made bundle identity depend on cache state

**Status: FIXED in the working tree.**

`DownloadedBytes` counts the bytes the content store did not already hold. The
store is a persistent, machine-level cache populated by every previous build;
whether it holds a given `.deb` is a fact about the machine, never about the
request. Recording it in `lock.json` meant the same `debark build` run twice
produced `downloaded_bytes` N and then 0 — different lock bytes, different
`LockDigest`, different `BundleID`, different `README.txt`, broken by nothing
more than having built the bundle once before.

Fixed by `stripCacheDependentStats`, following the precedent already set for
`Stats.DurationSeconds`: still reported exactly through `BuildResult` and
printed by the CLI, simply not a fact the bundle records about itself. The
contrast with `Added`/`Removed`/`Unchanged` is drawn correctly in the code —
those are computed against the previous contents of `Output.Path`, which an
auditor rebuilding from scratch has empty by definition.

### 5.3 — `RequestDigest` covered seven host paths

**Status: FIXED in the working tree.**

Fixed by `requestDigestInput` / `requestDigestOptions`: `Output` and
`SnapshotRef` excluded, `StoreDir` dropped outright, and `PolicyRef`,
`ApprovedKeysRef`, `EmbedBinary` plus the three input-path lists reduced to
basenames. The structural choice is the durable part: it is its own named type
rather than `BuildRequest` with fields zeroed, so a field added upstream lands
*outside* the digest by default and has to be added deliberately.

A third guard now backs both 5.1 and 5.3: `makeLockReproducible` walks the
finished lock by reflection and scrubs the work root and bundle directory from
**every** string reachable from it, immediately before the final write. This is
defence in depth, not a replacement for collaborator-side masking, and its own
comment gives the right reason: `apt.Backend` is an interface with more than one
implementation and no way to enforce a convention. It also closes the separate
finding that host temp paths reached `lock.json` **warnings** — those are built
from raw `err.Error()` text at several call sites in `core/apt` and were never
masked. Credentials are handled on the other side by `fetch.RedactURL`, now
applied across `core/fetch` and `core/engine` (the first review's F3).

### 5.4 — `manifest.Signature.CreatedAt` ignores `SOURCE_DATE_EPOCH`

**Severity:** High (as part of the determinism violation).
**Confirmed by code inspection.** **Status: OPEN.**

`core/engine/clock.go`'s `effectiveCreatedAt` is documented as "the ONLY
function in this package that decides what *now* means for a build's
artefacts", and that is true — *of that package*. `core/sign` is a different
package and calls the wall clock directly: `nowStamp()` is
`canonical.Time(time.Now())`, used by all three signers (`ed25519.go`,
`gpg.go`, `plugin.go`). `core/engine/finalize.go` writes the returned
`Signature` into `debark.manifest.sig` unchanged.

So `debark.manifest.sig` carries a `created_at` that moves with the wall
clock, and **no signed bundle is ever byte-identical to a rebuild** — the one
guarantee `SOURCE_DATE_EPOCH` was wired up to provide. Because
`canonical.Time` truncates to the second, two builds finishing within the same
second produce identical bytes, which is precisely what makes this intermittent
rather than obvious.

I could not confirm this by execution: `test/integration`'s `TestDeterminism`
— which now *does* compare the signature file — currently fails earlier, in
store ingestion, from the mid-flight `PutFile` changes described. The
code-level chain is unambiguous, so the finding stands; the round-trip
demonstration is owed once the tree is green.

## 6. `core/manifest`, `core/canonical` and `core/verify`

### 6.1 — Link substitution at a manifest-listed path

**Severity:** High. **Confirmed by execution** (hardlink case).
**Status: FIXED in the working tree.**

There was no entry-type check anywhere in `core/verify`. The bundle walk was
the only code that saw what `lstat` sees; every check under it opened the path
and followed wherever it led (`digest.SHA256File` uses `os.Open`,
`checkLockAndSnapshot` uses `os.ReadFile`). So a symlink or hardlink at a
manifest-listed path verified exactly like the bytes themselves — while the
data actually lived **outside the verified tree**, where it could be rewritten
between the moment verify hashed it and the moment apt read the same path,
without touching the medium that had just been approved. That converts the
narrow TOCTOU the first review recorded as F7 into "pre-position a file and
wait".

`core/bundle/tar.go` already refused `TypeSymlink` and `TypeLink` on import.
The actual gate in front of apt did not — which is the general lesson: a check
on the way in is not a check at the boundary, because the boundary is reachable
without the way in (an operator's own `tar -xf`, for one; tar restores symlink
targets verbatim, absolute targets included).

**Fixed** with a type gate placed first in `checkFiles` — before the manifest
lookup and before the manifest/signature skip — refusing any entry whose type
bits are set, so devices, sockets and FIFOs go the same way as links. A hard
link passes that gate legitimately (`lstat` reports a plain regular file,
because that is what it is), so a second check reads the link count via
per-platform `linkCount` helpers (`linkcount_unix.go`, `linkcount_windows.go`,
`linkcount_other.go`). Where the count cannot be had, it stands aside rather
than refusing — a check that read "I could not ask" as "more than one link"
would reject good bundles on filesystems that do not report it. Both raise
`ProblemFileNotRegular`.

**A follow-on defect this exposed.** `ProblemFileNotRegular` is a new value in
a published enum, and the enum is duplicated: `api/schema/verifyreport.v1.schema.json`
carries it, and `api/schema/installreport.v1.schema.json` carries its **own
local copy** of the same enum so that file validates standalone. A
hand-maintained `want` slice in `api/schema/schema_test.go` had drifted from
the Go constants, and nothing was checking the `installreport.v1` copy at all.
Both are now asserted against the same Go constants in one place. Worth
recording as its own defect class: **a duplicated constant list is a defect,
and the only thing that makes a copy safe is a test that it is still a copy.**
Widening a set lands in one file and not the other, silently, and the schema is
a published contract.

### 6.2 — `manifest.Load` had no structural validation and no size bound

**Severity:** Medium. **Confirmed by measurement.**
**Status: FIXED in the working tree. One residual OPEN.**

The manifest arrives on the same removable medium as everything else and is
read by verify **before any signature has been checked** — it has to be,
because the signature is over its bytes. Its size was therefore entirely
attacker-chosen, and nothing upstream constrained it (`tar.go` admitted an
8 GiB entry). Loading is not cheap in proportion: a measured 120.9 MiB manifest
cost 2,682 MiB of total allocation and 1,088 MiB of peak heap inside `Load`,
roughly 9×, because the raw bytes, the typed decode, the raw key map and the
JCS transform are all live at once. That is an out-of-memory kill of `debark
verify` on the **target**, from a file the target has not yet decided to trust.

Separately, `encoding/json` falls back to case-insensitive field matching, so a
document whose only version key was `SCHEMA_VERSION` loaded as schema v1 — and
its canonical bytes then carried a key no other implementation of the format
would recognise, with debark's own signature vouching for them.

**Fixed:** `readBounded` with `maxManifestSize` (16 MiB, ~3 orders of magnitude
above any real manifest); an exact-key check for `schema_version` against a
second raw-key decode; and `checkDocument` + `checkFilePath`, which enforce
required keys, non-negative sizes, well-formed digests, and a real path grammar
(relative, forward-slashed, cleaned, no control bytes, no drive letter, no
`..`).

**Residual, OPEN:** `LoadSignature` still reads `debark.manifest.sig` with a
bare `os.ReadFile` and no size bound. `core/verify` bounds the *number* of
signature blocks at 32 — with a good measurement behind it: a 29 MB `.sig`
holding 200,000 gpg blocks kept verify running past a minute, and the attacker
picks the label, so only a count bounds the cost — but the file's bytes are
still read whole into memory before that count applies.

### 6.3 — A manifest listing one path twice with contradictory digests verified

**Severity:** Medium. **Status: FIXED in the working tree.**

`checkFiles` built its coverage map last-wins while `findFile` resolved
first-wins, so a signed manifest could say two different things about one path
and satisfy both readers. Fixed at both ends: `checkDocument` refuses a
duplicate path outright at load, and `indexFiles` returns the duplicates it saw
so `Verify` raises `ProblemManifestMalformed` — *"the manifest is the one
signed object and must say exactly one thing about each path"*.

### 6.4 — `core/canonical` is not injective on invalid UTF-8

**Severity:** Medium. **Reasoning only** for the residual.
**Status: MITIGATED where it mattered; the underlying property is unchanged.**

Go's JSON encoder silently replaces an invalid UTF-8 byte with U+FFFD, so two
byte-different manifests differing only in invalid UTF-8 canonicalise — and
therefore **sign** — identically.

This is now refused where it was reachable and load-bearing: `checkFilePath`
rejects a file path that is not valid UTF-8, in both directions (`Build`
applies the same rule on the way out that `Load` applies on the way in), so the
signed serialisation of the file list stays unambiguous. `manifest.Load` and
`verify`'s digest checks also canonicalise the **raw bytes read from disk**,
never a re-marshalled struct — the first review's F9, still applied
consistently.

The residual is that `core/canonical` itself is unchanged, so the property
still holds for any other free-text field that reaches a canonicalised document
(lock warnings, `Unresolved.Detail`, snapshot labels). I did not construct a
case where that is exploitable, and `jcs.Transform`'s duplicate-key rejection
 closes the neighbouring differential; recorded so the next person to add a
signed free-text field knows the encoder's behaviour rather than discovering
it.

## 7. `core/repository`, `core/snapshot`, `core/install` and the CLI

### 7.1 — Control-field passthrough into `Packages`

**Severity:** Medium. **Status: FIXED in the working tree.**

A vendor `.deb`'s control paragraph was copied into the generated `Packages`
stanza field-for-field. debark appends its own `Filename`, `Size`, `MD5sum`,
`SHA1` and `SHA256`, but never wrote `SHA512:` — so a `.deb` declaring its own
`SHA512` produced a stanza where apt saw exactly one, the attacker's, and
`debRecordParser::Hashes()` prefers it. A `SHA512` naming some other file makes
apt fail at install time, **past the air gap**, where a failure is expensive
and hard to diagnose.

Fixed by `controlFields` and `validFieldName`, with `core/repository/hostile_input_test.go`
as a regression suite written from the attacker's side — each fixture is the
smallest hostile `.deb` or `Input` that produced a confirmed bad `Packages` or
`Release` before the corresponding check existed. Two neighbours went the same
way: `PoolFile.Path` is now checked before it becomes the `Filename:` URI apt
resolves (it could otherwise name a file outside the manifest-covered tree),
and `Release` field injection via `Codename` is refused by the same
`validFieldName` gate.

### 7.2 — Terminal control-sequence injection through snapshot free text

**Severity:** Medium. **Confirmed by execution.**
**Status: FIXED in the working tree** (`core/snapshot/displaystrings.go`, new
file).

A snapshot is untrusted input and several of its fields exist purely to be
printed. Nothing bounded how many warnings there were, how long each was, or
which characters they could contain. A captured "warning" carrying `ESC[1A
ESC[2K` scrolled back over the digest line in `snapshot inspect` output and
overwrote it with a **forged** one — confirmed.

That is aimed precisely at the human digest comparison `docs/threat-model.md`
§6 asks a reviewer to perform, which makes the reviewer's own terminal the
attack surface. It is the rarer kind of finding: the target is not the program
but the person auditing it.

Fixed by refusal rather than repair — `doValidate`'s contract is "decide
whether a document can be trusted at all", the same family of failure as a
digest mismatch, and a document whose display strings are driving the terminal
has already answered that question. Bounds on count and length; C0 tested per
byte and C1 per rune (a raw `0x9B` is not valid UTF-8 and a UTF-8 terminal will
not act on it, while an encoded U+009B is two bytes that it will). Capture
sanitises at the point of production, so an honest snapshot never writes a
document this refuses. The file's own comment correctly notes this bounds the
snapshot side only, and that the printing side needs its own sanitiser.

### 7.3 — `Archive.Digest` computed after re-redaction

**Severity:** Medium. **Status: FIXED in the working tree.**

`Archive.Digest` is what the lock and manifest record as `snapshot_digest`, and
the point of recording it is to answer "which snapshot file was this bundle
built from" — an answer a reviewer is meant to check over a second channel.
Digesting the *post*-normalisation document broke exactly that: two
byte-different archives, one carrying unredacted proxy credentials, normalised
to the same document and reported the same digest. Fixed by digesting as
delivered, before `reapplyRedactions`. On an honest snapshot the normalisation
is a no-op, so no digest anyone has seen moves.

### 7.4 — `install` reported a missing `gpg` binary as "media compromised"

**Severity:** Medium. **Status: FIXED in the working tree.**

`runner.go` wrapped every verifier error in `dferr.Verification`
unconditionally, so a machine with no `gpg` installed got exit 4 — which
ADR-012 gives the operator as *"the media is compromised, escalate"* — while
`debark verify` on the same machine, from the same bundle, said exit 2. The
wrap also discarded the cause's "install gnupg" hint. Fixed: only an
*unclassified* verifier error becomes `Verification`; an already-classified
cause is preserved, the same shape as `core/engine`'s `classify()`.

`dferr.ClassOf`'s doc comment was also simply wrong — it claimed the innermost
`*Error` when `errors.As` returns the outermost. That is now corrected, and the
corrected comment explains *why* outermost is the answer callers want (the last
package to classify is the one closest to the operator) and what follows from
it (re-wrapping an already-classified cause silently overrides its class — so
wrap conditionally). A doc comment that inverts the semantics of a function
used to choose exit codes is a real defect, not a typo: this one had already
produced the misclassification above.

### 7.5 — `--keep-source` installs a permanent `Trusted: yes` source, silently

**Severity:** Medium. **Confirmed by code inspection.** **Status: OPEN.**

`--keep-source` copies the bundle's `.sources` file into
`/etc/apt/sources.list.d/`. That stanza carries `Trusted: yes`, which is
correct *during* install — the manifest signature has just been verified, and
`Trusted: yes` on the private source is what the design calls for
(`docs/security-model.md`, "What `verify` actually checks"). Persisting it is
different: it leaves a permanent, unauthenticated apt source pointing at a
bundle directory that **nothing re-verifies**, and apt performs no independent
check of that repo's metadata. Anything later written into that directory is
installed on the operator's next unrelated `apt install`.

The flag is a deliberate, documented, opt-in exception, and that is fine. What
is missing is any warning at the moment it is used: `PersistSource`'s result is
only inspected on failure, and a success is silent. An operator gets no line
telling them what now permanently trusts what.

### 7.6 — Evidence-stream `Close` errors, and an e2e harness that blamed the product

**Severity:** Low. **Status: FIXED in the working tree.**

`evidence`'s `Sink` contract singles out the file sink as the one whose `Close`
error must not be swallowed, because it is usually the only durable copy of the
run. The CLI discarded it at all five call sites. Now handled centrally in
`internal/cli/context.go`'s `NewEvidenceSink`, which returns a close function
that reports the sink's error and the underlying file's, preferring the first —
with `internal/cli/evidence_close_test.go` covering it.

The e2e harness converted its own copy failures into product verification
failures, so a broken `CopyIn` was reported as "debark rejected a bundle it
should have accepted", and a failed walk reported an empty bundle. Fixed: every
copy now routes through `setBlocked` with the stage named, which is a harness
fault and reads as one; and the bundle walk propagates its errors rather than
skipping them. This matters more than its severity suggests — a test harness
that misattributes its own failures to the product trains everyone reading the
matrix to discount it.

## 8. Verified sound

A review that only lists problems is as misleading as one that only lists
reassurances. Each of these was checked in this review; where the check was an
execution rather than a reading, that is said.

- **Zero telemetry holds — proven, not asserted.** There is exactly one HTTP
  request call site in the tree (`core/fetch/fetcher.go`,
  `http.NewRequestWithContext` in `attempt()`), reachable only with
  operator-supplied URLs. **`go list -deps ./core/install` returns 129 packages
  with zero `net/*` among them** — target-side code physically cannot open a
  socket, which is a structural guarantee rather than a policy. No analytics,
  crash reporting or update check appears in any of the 68 modules.
- **Verify-before-apt holds on every install path.** Confirmed by execution
  against a full tamper matrix: every case exited 4, and none reached apt or
  dpkg. Structurally, `Plan` and `Apply` both funnel through one `execute()`
  whose first action is `r.deps.Verifier.Verify`, before the lock is loaded,
  before preconditions, before the private root exists. There is no second code
  path that skips it. `core/verify/tamper_test.go`, `links_test.go` and
  `sigblocks_test.go` now carry that matrix in-tree.
- **apt is the oracle.** No hand-rolled dependency solver, version-range
  satisfaction, candidate ranking or alternative selection anywhere.
  `core/apt/solver.go` *detects* which solver apt is using; it does not
  implement one. `core/apt/select.go` selects a *backend*, not a package.
  `CompareVersions` delegates to `pault.ag/go/debian/version` for the Policy
  §5.6.12 algorithm and exists only to compare two strings already in hand.
- **Manifest coverage has no attacker-usable excluded slot.** Exactly two paths
  are excluded from the manifest's own file list —
  `debark.manifest.json` and `debark.manifest.sig` — both compared
  root-relative after `filepath.Rel` and `ToSlash`, so a nested file of the same
  name is not excluded. Verify reports any unlisted file as
  `ProblemFileUnexpected`.
- **The first review's arbitrary-file-write (F1) is genuinely fixed**, with
  layered defence: `PoolPath` returns `""` for a name or filename that fails
  `ValidPackageName`/`ValidFilename`, *and* the caller refuses a destination
  that is not lexically inside the pool. `core/repository/poolpath_security_test.go`
  covers twelve hostile shapes including parent refs, absolute paths, drive
  letters, embedded NUL and newline.
- **Domain separation in signing is correct and applied identically on both
  sides.** `SigningInput` is `purpose ‖ 0x00 ‖ canonical`, and the verify side
  passes the constant `manifest.SignPurpose` — never a purpose read from the
  bundle, which is the mistake that makes domain separation decorative.
- **`jcs.Transform` rejects duplicate keys** (`gowebpki/jcs@v1.0.1`, "Duplicate
  key: …"), closing the canonicaliser-vs-parser differential where a document
  means one thing to the signer and another to the verifier.
- **Tar import refuses symlinks, hardlinks, device, FIFO and socket entries**
  — links by name and everything else through the `default:` arm, so a new
  type flag is refused rather than admitted — **and discards setuid, setgid and
  sticky bits**: `extractRegularFile` derives the mode as 0644 or 0755 from the
  execute bit alone, never from the header's mode.
- **No shell anywhere.** The only two `sh -c` uses are in
  `core/apt/container_driver.go`, both fixed string literals with no
  interpolation (a `const script` probe, and a fixed `cp -a` fallback).
- **The install path never re-resolves.** apt is handed exact
  `name:arch=version` triples read from the verified lock, and
  `splitInstallEntry` refuses an entry that is not in that form. ADR-007 holds.
- **Same-media key refusal remains correct** (the first review's F8) — including
  the path-separator-suffixed prefix check that stops a sibling `bundle-keys`
  directory from counting as "inside".

## 9. Process notes

### 9.1 — Reviewing stubs buys less than it looks like it does

The first review read `core/sign`, `core/verify`, `core/snapshot` and most of
`core/bundle` while they were stubs, and said so. It was right to publish
anyway: it caught F1, a real arbitrary-file-write, and it established the shape
of the trust boundary well enough that this review could test it rather than
rediscover it.

But almost every finding above lives in code that did not exist to be read:
the entry-type gate is a defect *of an implementation*, invisible in a
stub that has no walk; the store's missing content checks are defects of
an implementation that hardlinks; the gpg fingerprint mismatch required a
signer that actually shells out to gpg. The first review's F2 recorded that
`core/verify` and `core/sign` had "zero automated test coverage" and appeared
"correct on careful manual reading". Both halves were accurate. The reading was
careful, and it still could not see three High findings, because on a careful
manual reading a stub is correct.

The lesson is not "do not review stubs" — it is that **a review of a stub
expires the moment the stub is filled in**, and the record should say so
loudly enough that nobody mistakes the earlier sign-off for coverage. The
first record did say so. This one exists because it did.

### 9.2 — Tests that cannot express the failure

Several defects here sat under green tests. The pattern is worth naming,
because it is not "insufficient coverage" — the tests ran, asserted, and
passed. It is that the **fake could not express the failure**, so the assertion
was true of the fake and vacuous about the product.

The determinism test is the clearest case. It asserted byte-identical bundles
across two builds and passed, while three of the four violations were
live:

- Its fake backend never set `Resolver.APTOptions` at all, so the field where
  a host path had already been caught once could not carry one.
- Every build set `Options.ClosedWorldCheck = false`, so `CommandDigest` and
  `OutputDigest` — the two values that actually differed — were never computed.
  The check is on by default in production; the test turned off the code path
  it was meant to cover.
- Each build got its own private store, so both always downloaded everything
  and `DownloadedBytes` was equal by construction — the one arrangement under
  which a cache-dependent field looks deterministic.
- It excluded `debark.manifest.sig` from comparison, because each build used
  a throwaway key, so the file carrying `created_at` was never compared at all.

Three of those four are not coverage gaps; they are a test *designed* so the
failure cannot occur. The rewrite is instructive about the remedy: share one
store and one signing key between the two builds (so cache state and the
signature file are both in scope), leave the closed-world check at its default,
and drive the **real** local backend through a fake `Runner` rather than faking
the backend — so `BuildPrivateRoot`, the argv assembly and the digest
computation all run for real, and only the process that would have been `exec`'d
is fake.

The gpg round-trip test is the same shape in miniature: it generates a
key with **no signing subkey**, so the primary fingerprint and the signing
fingerprint are the same string and a comparison of two different things passes
by coincidence. The fixture excluded the only case that distinguishes correct
from incorrect.

`api/schema/schema_test.go` is a third variant: the test existed and
compared a schema enum against a hand-maintained `want` slice — a second copy
of the thing under test, which drifts. And it checked only one of the two schema
files carrying that enum.

Three questions that would have caught all of these, and are cheap to ask of any
test that guards a security property:

1. **Can this fake produce the failure at all?** If the seam is stubbed out or
   the flag is off, the assertion is about the harness.
2. **Is the fixture the easy case?** A key with no subkey, an empty store, a
   fresh output directory — each removes the distinction the test exists to
   draw.
3. **Is the expected value a second copy of the actual?** Then the test proves
   the copies agree, not that either is right.

### 9.3 — Documentation that outlived the code it described

Two gaps were found, both belonging to the top-level docs rather than this
review's own scope. **Both were closed during this review**, which is why
they are recorded as history rather than as open items — but the shape is
worth keeping, because it recurs whenever a security fix widens a check.

- **`docs/security-model.md` described the pre-fix verify.** Steps 4 and 5 of
  the numbered check list read "Every file the manifest lists exists, at the
  recorded size and digest" and "No file is present that the manifest doesn't
  list" — neither mentioned that the entry must be a **regular file carrying
  its own bytes**, which is now the first thing `checkFiles` enforces and the
  one that closes §6.1. As written, the document described a check that a
  symlink passes, which is precisely the reassurance an approver would have
  relied on. Now fixed: steps 4 and 5 carry the regular-file and link-count
  requirement, with a paragraph explaining that "the absence of them was a live
  hole".
- **`docs/threat-model.md`'s attack table had no row for link substitution.**
  The table ran to twelve rows — same-media keys, `Packages`/`Release` edits,
  `lock.json` downgrades, `--allow-unsigned` misuse — and nothing covered
  "replace a manifest-listed path with a link to bytes outside the verified
  tree". Now row 13, naming both ends of the defence (`tar.go`'s import refusal
  and `checkFiles`' walk), the `ProblemFileNotRegular` verdict, the deliberate
  fail-open on filesystems that cannot report a link count, and the fact that
  the row records a confirmed High defect now closed.

The general point: a check list in a security document is an assertion about
the code, and it decays silently. When a fix widens what `verify` refuses, the
document that enumerates what `verify` refuses is part of the fix — otherwise
the artefact an approver actually reads still describes the vulnerable
version.
